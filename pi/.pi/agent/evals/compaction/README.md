# Compaction retention eval

Measures what a compaction method keeps in the model's context, and what that costs, by replaying a session through Pi's real compaction code. It makes no model calls, so a run is fast, free and deterministic.

It answers two questions for each method:

1. **Retention.** After replay, is each commitment (a rule or decision the user stated only in chat) still in the context the model would see? Word for word, partly, or gone?
2. **Cost.** How large is the context after each compaction, and how many tokens are sent over the whole replay?

Presence is a proxy, not the outcome. The study this follows ([arXiv 2610.20116](https://arxiv.org/abs/2610.20116), Table 7) found that a model honours a rule far more often when the rule is in its context, but presence does not guarantee it. A behavioural probe, where a model answers a follow-up message, is a possible second stage and is not built yet.

## How a replay works

1. Load the session file and take the active branch (the path from the last entry back to the root).
2. Drop the session's own compaction entries, so every method starts from the same raw history.
3. Append each message to an in-memory `SessionManager`. Before each assistant message, estimate the context with Pi's `estimateTokens`. If it is above `window - reserveTokens`, compact, as Pi does before each request.
4. Compaction calls Pi's real `prepareCompaction`, then the method under test. For pi-vcc, that is its real `session_before_compact` handler, loaded from the installed package with your `pi-vcc-config.json`.
5. At the probe point, build the context with `buildSessionContext` and score each commitment.

Pi's own trigger reads the provider's usage numbers. The replay uses the pure estimate, because the usage stored in a session reflects the compactions that happened then, not the ones being replayed.

## Methods

| Name | What it does |
|---|---|
| `none` | Control. Never compacts. Every commitment must score intact; if not, the harness is broken. |
| `pi-vcc` | The installed `@sting8k/pi-vcc` compaction hook. |
| `pi-vcc+rules[:N]` | Experiment. pi-vcc's summary plus a "Standing rules" section appended to the summary: sentences from the user's messages that match generic rule wording (`extensions/standing-rules/rules.ts`), verbatim, newest first within `N` characters (default 4000). |
| `pi-vcc+inject[:N]` | What the live `standing-rules` extension does, using its own code: pi-vcc's summary unchanged, plus the rules from the summarized user messages injected as a message right after it. |

Candidates (for example, pinning user messages) are added as new methods in `variants.ts`. A method may compact, transform the context afterwards, or both.

## Window profiles

| Profile | Window | Reserve | Keep recent | Why |
|---|---|---|---|---|
| `real` | 200,000 | 20,000 | 30,000 | Your Opus 5.5 settings |
| `stress` | 48,000 | 16,384 | 20,000 | Pi defaults at the paper's window; forces many compactions |

## Cases

A case file is JSON:

```json
{
  "cases": [
    {
      "id": "migrations-rule",
      "session": "path/to/session.jsonl",
      "probeAt": "end",
      "commitments": [
        { "id": "no-migrations", "kind": "constraint", "keys": ["Don't touch the migrations folder", "except to add files under migrations/pending"] }
      ]
    }
  ]
}
```

- `keys` are exact substrings, compared after collapsing whitespace. Each key must appear exactly once in the source session; otherwise the case is invalid, since a later restatement would hide a loss.
- `probeAt` is `"end"` or an entry id. The replay stops before that entry.
- Include the qualifying clause of a rule as its own key. Losing it is the failure the study found most often.

Real-session cases hold private text, so they live under `.pi/evals/compaction/` (ignored by git). Synthetic cases are generated by `synthetic.ts` and are safe to commit.

## Scoring

Each commitment scores:

- **intact**: every key is in the context.
- **partial**: some keys are in the context.
- **absent**: no key is in the context.
- **invalid**: a key does not appear exactly once in the source session.
- **error**: the replay failed (missing file, a method threw). Never counted as absent.

It also records where the keys were found: the compaction summary, or the kept messages after it.

## Verdict rules

Frozen before any candidate is run:

- **Better**: more commitments intact than pi-vcc on the same cases and profile, no commitment that pi-vcc kept intact lost, and the context after compaction no more than 2× pi-vcc's median.
- **Worse**: any commitment lost that pi-vcc kept, or an error the baseline did not have.
- **Inconclusive**: anything else. Say what would settle it: more cases, not more runs (the replay is deterministic).

## Commands

```sh
# Unit tests and harness sanity checks
node --test evals/compaction/test/*.test.ts

# Run a case file
node evals/compaction/run.ts --cases .pi/evals/compaction/cases.json --variants none,pi-vcc --profiles real,stress
```

Results are written to `.pi/evals/compaction/results/<timestamp>/` as `results.json` and `report.md`.
